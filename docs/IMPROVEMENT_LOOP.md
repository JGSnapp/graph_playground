# Алгоритм улучшения системы

Рабочая инструкция для того, кто (человек или агент) улучшает движок расстановки.
Цель цикла — чтобы **каждое изменение было измерено**, а не «кажется, стало лучше».

Читать вместе с [QUALITY_MODEL.md](QUALITY_MODEL.md) (что мерим)
и [SYSTEM_v1.0.md](SYSTEM_v1.0.md) (что есть).
Журнал прогонов — [EXPERIMENTS.md](EXPERIMENTS.md).

---

## 0. Правила, которые не нарушаются

1. **Одна гипотеза — один эксперимент.** Меняешь промпт и добавляешь тул
   одновременно — результат не интерпретируем.
2. **Пул задач заморожен.** Задачи в `bench/tasks.ts` не редактируются; новые
   добавляются с новым id. Иначе сравнение с прошлыми прогонами теряет смысл.
3. **Каждый механизм отключаем.** Любая новая эвристика, тул или блок промпта
   должны выключаться флагом настроек или удалением одной строки из реестра.
   Сильные модели через полгода могут не нуждаться в костылях, которые нужны
   сегодня.
4. **Метрика не заменяет глаза.** `score 100` при уродливой картинке —
   это дефект метрики, и он важнее, чем сам прогон. Записывай такие случаи
   отдельно.
5. **Не подгонять метрику под результат.** Если правишь веса в `quality.ts`,
   старые прогоны пересчитываются заново, и это отмечается в журнале как смена
   мерной ленты (`M`-запись), а не как улучшение.

## 2. Шаг 1. Откуда берутся гипотезы

По убыванию ценности источника:

1. **Визуальный разбор PNG.** Самый честный источник. «Схема читается как лента»,
   «две группы слиплись», «стрелка идёт через полдоски».
2. **Лог отказов.** `refusals` в результате прогона. Повторяющийся отказ —
   это либо кривой гейт, либо непонятная агенту политика.
3. **Расход итераций.** Прогон в 30 итераций там, где хватает 10, — дефект
   инструментов, а не модели.
4. **Разрыв между моделями.** Если сильная модель справляется, а слабая нет —
   лечится инструментом или промптом. Если не справляется никто — лечится
   алгоритмом на стороне системы.
5. **Разрыв между метрикой и картинкой.** Высокий score при плохом виде —
   заводим новую метрику.

## 3. Шаг 2. Куда можно вносить изменение

Уровни перечислены в порядке «сначала дешёвое»:

| Уровень | Файл | Цена | Когда |
|---|---|---|---|
| L1. Промпт | `settings/defaults.ts` | минуты | правило понятно словами и модель его просто не знает |
| L2. Скилл | `skills/seed.ts` | минуты | правило нужно только в одном сценарии |
| L3. Ответ тула | `tools/*.ts` | часы | агент делает верный вызов, но не понимает результат |
| L4. Гейт/политика | `tools/*.ts` | часы | агент делает то, что нужно запретить |
| L5. Новый тул | `tools/*.ts` + реестр | день | агенту не хватает возможности или наблюдения |
| L6. Метрика | `shared/quality.ts`, `intersections.ts` | день | система не видит дефекта, который видит человек |
| L7. Алгоритм | `shared/routing.ts`, новый layout-модуль | дни | ни одна модель не справляется вручную |

**Правило выбора уровня:** не поднимайся на уровень выше, пока не проверил,
что нижний не работает. Автоматическая раскладка (L7) — последнее средство,
а не первое: она отбирает у агента контроль, который в этом продукте является
целью.

## 4. Шаг 3. Как запускать прогон

```bash
# 1. сервер стенда (отдельная data-директория, боевые доски не трогаются)
TECA_DATA_DIR=./bench/data PORT=5199 node_modules/.bin/tsx server/src/index.ts

# 2. основной прогон — дешёвая модель, полный пул
node_modules/.bin/tsx bench/run.ts --exp=E07 --task=all --model=deepseek-v4-flash --concurrency=2

# 3. только когда дешёвая модель даёт вменяемый результат — подтверждение на дорогой
#    (одна доска на claude ≈ $1.6, поэтому две-три задачи, а не весь пул)
node_modules/.bin/tsx bench/run.ts --exp=E07x --task=wiki-anime,dense-arch \
  --model=claude-sonnet-5 --allow-expensive
```

Требования к прогону:
- **тот же набор моделей**, иначе сравнивать нельзя;
- сервер перезапущен после правки кода (`tsx` без watch не перечитывает файлы);
- при правке промпта в `defaults.ts` — `tsx bench/sync-prompt.ts bench/data`,
  иначе прогон пойдёт на старом промпте.

### Деньги

Шлюз **резервирует** по `prompt + max_tokens`, а не списывает по факту, и резерв
держится против всего баланса — один неосторожный параллельный прогон дорогой
модели блокирует и дешёвые. Поэтому стенд:

- по умолчанию гоняет только дешёвые модели (`deepseek-*`, `claude-haiku`);
- дорогие требуют явного `--allow-expensive`;
- параллельность максимум 2 и только для дешёвых, с дорогой — всегда 1;
- отказывается стартовать, если оценка выше `--budget-run` (на доску, по умолчанию
  25 единиц) или `--budget-exp` (на весь эксперимент, по умолчанию 400),
  и подсказывает подходящий `maxTokens`.

Единица шлюза — не доллар: по его собственным оценкам против публичных прайсов
выходит ≈65 единиц на доллар (подробности в [CHANGES_v1.1.md](CHANGES_v1.1.md)).
Порядок величин, на который стоит опираться: полный пул из 8 задач на
`deepseek-v4-flash` — около $0.30, тот же пул на `claude-sonnet-5` — около $13.
Поэтому дешёвая модель гоняется на всём пуле сколько угодно раз, а дорогая —
точечно, на двух-трёх задачах.

Порядок правильный именно такой: сначала дешёвая модель на всём пуле, дорогая —
только чтобы подтвердить уже видимый результат. Дорогая модель на сыром изменении
не приносит информации, которой не дала бы дешёвая.

После прогона смотри строку с токенами: она печатается в конце и лежит в
`usage` каждого результата.

## 5. Шаг 4. Какие числа смотреть

Из `bench/report.ts`:

| Показатель | Хорошо | Что означает |
|---|---|---|
| средний `score` | растёт | общее качество |
| доля `ok` | растёт | доля прогонов без жёстких дефектов |
| `отказы` | падает | сколько раз агент упёрся в гейт |
| `итераций` | падает при том же score | эффективность процесса |
| `A×A` (наложения) | 0 | самое дорогое нарушение |
| `←→A` (стрелка сквозь блок) | 0 | второе по цене |
| `separation` | > 1.5 | связанное стоит ближе, чем несвязанное |
| `aspect` | → 1..2 | композиция не выродилась в ленту |
| `spread` | → 1.5 и ниже | нет одной связи, протянутой через всю доску |

### Сколько шума в одном прогоне

Измерено (E07, шесть графовых задач по три повтора на `deepseek-v4-flash`):

| задача | медиана | разброс между повторами |
|---|---|---|
| tree-org | 60 | **48** |
| fix-broken | 85 | 22 |
| wiki-anime | 55 | 18 |
| states-order | 68 | 17 |
| dense-arch | 22 | 8 |
| extend-existing | 53 | 3 |

Медианный разброс — **18 пунктов**. Причина не в движке: на двух подряд прогонах
модель делала тот же граф из тех же восьми узлов, но с размером карточки 240×180
вместо 240×140, и пересечений становилось 8 вместо 1.

Отсюда правила, которые нарушать нельзя:

1. **Один прогон на задачу — это не измерение.** Минимум три повтора,
   `bench/run.ts --repeat=3`, сравнение по медиане.
2. **Разница меньше разброса — не результат.** Отчёт помечает такие случаи
   словами «в пределах разброса»; принимать их за улучшение нельзя.
3. Изменение считается улучшением, если медиана по пулу выросла заметно больше
   разброса **или** выросла доля прогонов без жёстких конфликтов, и при этом
   ни один показатель не просел.

Я дважды нарушил это правило до того, как измерил шум, и оба раза принял
случайность за эффект правки.

## 6. Шаг 5. Визуальный разбор

Открыть `bench/out/<exp>/<task>__<model>.png` и ответить письменно:

1. Читается ли структура за 3 секунды? Где верх, где низ потока?
2. Видно ли группы без подписей?
3. Есть ли линия, которая идёт через всю схему?
4. Влезает ли текст в карточки, не обрезан ли?
5. Есть ли лишнее пустое место или, наоборот, слипшийся ком?
6. **Что из увиденного метрика не поймала?**

Пункт 6 — главный. Он порождает записи `M` (новая метрика) в журнале.

## 7. Шаг 6. Запись в журнал

Каждый эксперимент — блок в `EXPERIMENTS.md` по шаблону:

```markdown
### E07 — короткое название гипотезы

- **Тип:** P (промпт) | S (скилл) | T (тул) | G (гейт) | M (метрика) | A (алгоритм)
- **Гипотеза:** что плохо и почему предлагаемое изменение это чинит
- **Изменение:** файлы, флаг отключения
- **База сравнения:** E06
- **Числа:** score 62 → 71, ok 25% → 50%, отказы 4.1 → 1.2, итер 22 → 15
- **Глазами:** 2–5 предложений, что стало видно лучше и что осталось
- **Вердикт:** принято / откачено / принято под флагом `xxx`
- **Побочные наблюдения:** что заметили попутно, кандидаты в следующие гипотезы
```

## 8. Критерий остановки всей работы

Цель — «почти идеальные графы». Формально:

На полном пуле из 8 задач, на всех трёх моделях (24 прогона):
- средний `score` ≥ 85;
- доля прогонов с `ok=true` ≥ 70%;
- **ноль** наложений артефактов и **ноль** стрелок, режущих блоки, во всех прогонах;
- `fidelity` ≥ 0.8, `aspect` в диапазоне 0.5–2.5;
- визуальный разбор: ни одной схемы с вердиктом «не читается».

Промежуточные ворота, чтобы видеть движение:
- **Ворота 1:** ноль наложений и ноль разрезанных блоков на всём пуле.
- **Ворота 2:** средний score ≥ 70 и отказов < 1 на прогон.
- **Ворота 3:** целевые значения выше.
